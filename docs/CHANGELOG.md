## 2026-10-07 · Чек-лист «Проверка по ТЗ» (задание 4)

Ветка: `feature/tz-checklist` (от `frontend/camera`). API обратно совместимо:
в ответ `/api/analyze` добавлено поле `tz_checklist`, в `verdict.defects` — поле `category`.

### Зачем

ТЗ перечисляет 4 типа дефектов: разрыв на дорожках, непропаянные элементы,
повреждение компонентов, иные. Раньше отчёт показывал классы модели
(`dry_joint`, `short_circuit`, …), и связь с формулировкой задания жюри
приходилось угадывать. Теперь под вердиктом — чек-лист ровно по пунктам ТЗ.

Ключевой момент — честность: если активная модель вообще не умеет искать
дефекты пункта (например, бейзлайн с HF не знает `open_circuit`), пункт
помечается «не проверяется», а не «не найдено».

### По файлам

#### `backend/app/config.py`
- `TZ_CATEGORIES` — 4 пункта ТЗ (id + формулировка из задания), `DEFAULT_CATEGORY = "other"`.
- В правилах `VERDICT_RULES` у каждого класса поле `category`:
  `open_circuit` → разрыв дорожек; `dry_joint` → непропай;
  `incorrect_installation` → повреждение компонентов с `approximate: True`
  (это неправильная установка, а не повреждение — помечается в отчёте);
  `pcb_damage` (повреждение самой платы), `short_circuit`, `missing_hole`,
  `mouse_bite`, `spur`, `spurious_copper` → иные дефекты.

#### `backend/app/model_manager.py`
- `class_names()` — какие классы модель умеет находить: у `YoloModel` из
  `model.names` (после загрузки весов), у `MockModel` — классы заглушки,
  по умолчанию `None` (неизвестно → считаем, что проверяются все пункты).

#### `backend/app/verdict.py`
- `_evaluate_group()` добавляет в группу `category`.
- `build_tz_checklist(defects, model_classes)` — для каждого пункта ТЗ:
  найденные дефекты (без классов с `severity: ok`), покрытие классами модели,
  признак приближения; `state` = `reject` / `warning` / `clear` / `not_checked`,
  `found` — тексты найденного, `note` — пояснение.

#### `backend/app/schemas.py`, `backend/app/routers/analyze.py`
- `DefectGroup.category`; новая схема `TzCheckItem`; `AnalyzeResponse.tz_checklist`.
- Чек-лист строится по классам той модели, что реально считала кадр.

#### `frontend/index.html`, `frontend/js/photo.js`, `frontend/css/style.css`
- Блок «Проверка по ТЗ» под вердиктом: значок состояния (✖ / ! / ✓ / —),
  формулировка пункта, что найдено или «не найдено» / «не проверяется»,
  пояснение курсивом. Скрывается при ошибке анализа.

#### `docs/API.md`
- Пример `tz_checklist` и описание состояний.

### Как проверено

| Сценарий | Результат |
|---|---|
| Бейзлайн HF, найден непропай | разрыв — не проверяется; непропай — ✖; компоненты — ✓ (приближённо); иные — ✓ |
| DeepPCB, 2 разрыва + заусенец | разрыв — ✖ «разрыв дорожки ×2»; непропай и компоненты — не проверяются; иные — ! |
| Бейзлайн HF, чистая плата | всё ✓, кроме разрыва (не проверяется) |
| Классы модели неизвестны | все пункты ✓ |
| Неизвестный класс модели | попадает в «иные дефекты» |
| Браузер, mock-режим | блок отрисован: 2 × «не проверяется», 2 × «найдено» |

### Заметка для ML

- Имена классов своей модели должны совпадать с ключами `VERDICT_RULES`
  (`open_circuit`, `missing_hole`, `mouse_bite`, `spur`, `spurious_copper`, `short_circuit`).
  Класс с другим именем (например, `short` или `open` из исходной разметки DeepPCB)
  попадёт в «иные дефекты» без русского названия.
- Пункт «повреждение компонентов» закрыт только приближением — нужен датасет
  с повреждёнными компонентами.

## 2026-10-07 · Backend: вердикт с учётом количества и площади дефектов

Ветка: `backend/fixes`. API обратно совместимо: в `verdict` добавлено поле
`defects`, формат `status` / `reason` прежний (поменялись только тексты).

### Что было

Правило «есть хоть один reject-класс → брак, иначе warning-класс → предупреждение».
`image_size` в `build_verdict` передавался, но не использовался. Один крошечный
`mouse_bite` и десять таких же давали одинаковый вердикт; повреждение платы любого
размера — всегда только предупреждение.

### По файлам

#### `backend/app/config.py`
- `VERDICT_RULES` из `{класс: "reject"}` стал `{класс: {правило}}`:
  - `severity` — базовая критичность одного дефекта (`reject` / `warning` / `ok`);
  - `reject_count` — столько дефектов класса и больше → брак;
  - `reject_area_pct` — суммарная площадь класса в % от кадра, с которой → брак.
- Пороги: `pcb_damage` → брак от 1% площади; `mouse_bite`, `spur` → брак от 3 шт.;
  `spurious_copper` → от 3 шт. или от 1% площади. Остальные классы без изменений.
- Ограничение: процент считается от **кадра**, а не от платы (плата отдельно не
  сегментируется). Для снимков крупным планом это близкие величины.

#### `backend/app/verdict.py` (переписан)
- `detection_area()` — площадь дефекта: по полигону маски (формула шнурования),
  у моделей детекции — по рамке. Маска точнее: рамка вокруг тонкой
  диагональной трещины в разы больше самой трещины.
- `_evaluate_group()` — детекции группируются по классу; статус группы =
  `severity`, повышается `warning → reject` при превышении порога; в `note`
  записывается, какой порог сработал.
- `build_verdict()` — итог = худший статус среди групп; группы сортируются
  (брак первым, затем по количеству). `reason` перечисляет причины брака и
  отдельно «Также проверить: …» для предупреждений. Возвращает `defects`.
- Класс, которого нет в правилах, — `warning` (как и раньше).
- Числа в тексте по-русски: `1,5%`, `2%` (без «,0»).
- Комментарий про `RU_LABELS`: фронтенд получает русские названия в
  `verdict.defects[].label`, вторая копия в `frontend/js/shared.js` больше
  не обязательна (перевод фронтенда на неё — отдельным шагом).

#### `backend/app/schemas.py`
- Новая схема `DefectGroup {class_name, label, count, area_pct, status, note}`.
- `Verdict.defects: list[DefectGroup]` (по умолчанию пустой).

#### `docs/API.md`
- Пример ответа `/api/analyze` с `defects`, описание полей, правила вердикта
  и таблица примеров `reason`.

### Как проверено

`build_verdict` на кадре 1000×1000 (1% = 10 000 px²):

| Детекции | Итог | reason |
|---|---|---|
| нет | ok | Дефектов не обнаружено |
| 2 × open_circuit | reject | Брак: разрыв дорожки ×2 |
| 1 × mouse_bite | warning | Требует проверки оператора: дефект края дорожки («мышиный укус») |
| 3 × mouse_bite | reject | Брак: … — 3 шт. (порог брака — 3) |
| pcb_damage 0,5% | warning | Требует проверки оператора: повреждение платы |
| pcb_damage 2% | reject | Брак: повреждение платы — 2% площади (порог брака — 1%) |
| неизвестный класс | warning | Требует проверки оператора: alien_blob |
| dry_joint + spur | reject | Брак: непропаянный элемент. Также проверить: заусенец дорожки |
| pcb_damage 2%, без image_size | warning | порог площади не применяется (`area_pct = null`) |

Площадь треугольной маски 100×100 — 5000 px² (рамка дала бы 10 000).
`POST /api/analyze` в mock-режиме отдаёт `verdict.defects`, схема
`DefectGroup` видна в Swagger.

## 2026-10-07 · Backend: неблокирующий инференс, сглаживание по IoU, загрузка моделей

Ветка: `backend/fixes`. API обратно совместимо: в `GET /api/models` добавлено
одно необязательное поле `error`, остальные ответы не изменились.

### Кратко

| # | Проблема | Последствие на демо | Решение |
|---|---|---|---|
| 1 | Инференс выполнялся прямо в event loop | Пока модель считает кадр, сервер не отвечает никому (health, камера, переключение) | `run_in_threadpool` + `threading.Lock` на модели |
| 2 | Сглаживание считало кадры по классу | Два дефекта одного класса в кадре → +2 за кадр → «подтверждение» с первого кадра, мерцание; разные дефекты склеивались | Треки по месту на кадре (сопоставление рамок по IoU) |
| 3 | Сглаживатель не сбрасывался при смене модели | Рамки старой модели «доживали» на экране | `frame_smoother.reset()` при активации + отбрасывание кадров «старой» модели |
| 4 | `GET /api/models` грузил веса всех моделей | Открытие страницы = загрузка всех весов (секунды) | `is_loaded()` только проверяет; загрузка — `load()`; прогрев активной на старте |
| 5 | Активация модели с битыми весами | Демо переключалось на неработающую модель | Сначала загрузка, переключение только при успехе (иначе 503) |
| 6 | `/api/health` пытался импортировать ultralytics при каждом вызове | Лишняя работа раз в 10 секунд | Проверка один раз на старте через `importlib.util.find_spec` |

### По файлам

#### `backend/app/routers/analyze.py`, `backend/app/routers/live.py`
- `manager.get_active().predict(img)` → `await run_in_threadpool(model.predict, img)`.
  FastAPI крутит все `async`-обработчики в одном потоке (event loop); синхронный
  `predict()` на сотни мс замораживал его целиком. Теперь инференс идёт в пуле
  потоков, event loop свободен.
- Активная модель запоминается в переменную `model` **до** инференса: если её
  переключат во время обработки, в поле `model` ответа и в тексте ошибки будет
  id той модели, что реально считала (раньше — `manager.active_id`, уже новый).
- `live.py`: если пока кадр считался, активная модель сменилась — результат
  не подаётся в сглаживатель (возвращается пустой список детекций), чтобы
  детекции старой модели не попали в только что сброшенное состояние.
- Сглаживатель по-прежнему вызывается в event loop, а не в потоке: он быстрый,
  а так к его состоянию никогда не обращаются два потока одновременно.

#### `backend/app/model_manager.py`
- `BasePcbModel`: новые `load()` и свойство `load_error`; `is_loaded()` по
  контракту больше **ничего не грузит**.
- `YoloModel`:
  - `_ensure_loaded()` заменён на `load()`: грузит веса, при ошибке запоминает
    текст в `_load_error` и пробрасывает исключение;
  - `is_loaded()` — просто `self._model is not None`;
  - `threading.Lock`: и загрузка, и `predict` ultralytics идут под локом —
    модель не потокобезопасна, а с пулом потоков фото и кадр камеры могут
    прийти одновременно. (Внимание: `time_ms` включает ожидание лока.)
- `ModelManager`:
  - `has(id)`, `ids()`, `get(id)` — публичная замена обращениям к `_models` из роутеров;
  - `warmup_active()` — загрузка весов активной модели; ошибку не бросает,
    чтобы сервер поднимался и без весов;
  - `list_models()` отдаёт новое поле `error` и ничего не грузит.

#### `backend/app/routers/models.py`
- `POST /api/models/{id}/activate`:
  1. 404, если id неизвестен (список доступных — через `manager.ids()`);
  2. загрузка весов в пуле потоков; при ошибке — **503**, активной остаётся прежняя модель;
  3. переключение + `frame_smoother.reset()`.
- `GET /api/models` отвечает мгновенно.

#### `backend/app/smoothing.py` (переписан)
- Функция `iou(a, b)` — Intersection over Union двух рамок `[x1, y1, x2, y2]`.
- Состояние — список треков `{class_name, det, streak, shown, last_seen_ms}`
  вместо словаря по классам.
- Алгоритм `process()` за кадр:
  1. детекции по убыванию уверенности ищут незанятый трек того же класса
     с максимальным IoU ≥ `SMOOTH_IOU_MATCH`; не нашли — новый трек;
  2. у найденного трека `streak += 1` (ровно +1 за кадр), обновляются рамка и время;
  3. треки без детекции в кадре — `streak = 0`;
  4. показ: `streak >= CONFIRM_FRAMES` → показан; не видели дольше `HOLD_MS` → скрыт;
  5. удаляются треки, которые не показаны и не видны в текущем кадре.
- `reset()` — полная очистка состояния.
- Параметры конструктора проверяются через `is None`: раньше `hold_ms=0`
  из-за `0 or HOLD_MS` молча превращался в 500.

#### `backend/app/config.py`
- Новый параметр `SMOOTH_IOU_MATCH = 0.3` — минимальное перекрытие рамок
  соседних кадров, чтобы считать их одним дефектом. Меньше — терпимее к тряске
  камеры, но выше риск склеить соседние дефекты. Подбирать на реальном потоке.

#### `backend/app/main.py`
- `lifespan`: прогрев активной модели (`manager.warmup_active()` в пуле потоков)
  до приёма первого запроса — первый кадр камеры не ждёт загрузки весов.
- `ML_AVAILABLE` вычисляется один раз через `importlib.util.find_spec("ultralytics")`
  (ищет пакет без импорта); `/api/health` отдаёт готовое значение.
- Убран неиспользуемый `from pathlib import Path`.

#### `backend/app/schemas.py`
- `ModelInfo.error: Optional[str] = None` — текст ошибки последней загрузки весов.

#### `docs/API.md`
- `GET /api/models`: поле `error`, новая семантика `loaded` (не грузит, отвечает мгновенно).
- `POST /api/models/{id}/activate`: ошибка 503 (прежняя модель остаётся активной),
  сброс сглаживания при переключении.

### Как проверено

Скрипты в mock-режиме (`USE_MOCK=true`) и в «реальном» режиме без весов (`USE_MOCK=false`):

| Проверка | Результат |
|---|---|
| Два `dry_joint` в разных местах: кадр 1 / кадр 2 | 0 / 2 показано (независимые треки, подтверждение со 2-го кадра) |
| Один из двух дефектов пропал | удерживается `HOLD_MS` |
| `hold_ms=0`, дефект пропал | скрыт сразу (до фикса — висел 500 мс) |
